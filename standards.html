01 / THE RATIFIED BASELINE

先读已发布标准，
再看研究方案。

NIST 已发布 FIPS 203、204 和 205。前两项是格基标准；第三项是基于散列的签名，有助于明确 PQC 的范围。

FIPS 203 · FINAL · LATTICE-BASED

ML-KEM

基于 Module-LWE 相关困难性的密钥封装。KeyGen 产生公私钥；Encaps 产生密文和共享秘密；Decaps 恢复共享秘密。标准给出 ML-KEM-512、768、1024 三个参数集。

密钥建立共享秘密不是身份认证
阅读 NIST FIPS 203 ↗
FIPS 204 · FINAL · LATTICE-BASED

ML-DSA

模格数字签名。KeyGen 生成签名密钥；Sign 对消息产生签名；Verify 检查签名。用途是消息完整性与签名者认证，不负责协商共享秘密。

数字签名公钥验证不是 KEM
阅读 NIST FIPS 204 ↗
FIPS 205 · FINAL · HASH-BASED

SLH-DSA

无状态、基于散列的后量子签名。它是 PQC 正式标准，却不属于格密码。把它放在这里，是提醒自己不要把所有后量子签名都画进格的问题树。

阅读 NIST FIPS 205 ↗
NIST SP 800-227 · FINAL · KEM GUIDANCE

怎样安全使用 KEM

这份建议解释 KEM 的定义、属性、实现和使用方式。它比直接从 ML-KEM 的多项式伪代码开始，更适合作为工程接口入口。

阅读 NIST SP 800-227 ↗

Falcon / FN-DSA 属于另一条格基签名方向；截至 2026.09.24，NIST 标准化页面仍将 FIPS 206 标为制定中。状态可能变化，请以 NIST 官方状态页 ↗为准。

02 / PROTOCOL INTERFACES

KEM 建立秘密；
签名证明来源。

格的困难性不是协议设计的替身。TLS、VPN、证书或固件更新各自还需要身份、版本、密钥生命周期与故障策略。

KEY ENCAPSULATION

KeyGen → Encaps → Decaps

Encaps(pk) → (ct, ss)
Decaps(sk, ct) → ss

发送方用接收者的公钥封装，共享秘密随后交给对称密码。只拿到公钥并不等于已验证身份；身份绑定要由协议完成。

DIGITAL SIGNATURE

KeyGen → Sign → Verify

Sign(sk, message) → signature
Verify(pk, message, signature) → valid?

验证者检查消息与签名是否匹配。密钥来源、证书链和撤销状态仍是系统层问题；签名算法本身不会自动解决信任。

03 / IMPLEMENTATION REVIEW

toy code 讲明白原理，
生产安全还要过六关。

现有仓库刻意使用小参数和透明代码，便于看清数学。下面这些要求应在成熟实现、协议和验证流程中审查。

01 / PARAMETERS

参数与攻击成本

核对正式参数集、已知经典与量子攻击模型、所需安全强度。二维图和 tiny 暴力搜索不能作为安全证明。

02 / SAMPLING

随机数与分布

secret、噪声和随机种子的分布必须符合规范；偏差、重用或低熵会破坏安全假设。

03 / CCA BOUNDARY

解封装与错误处理

关注选择密文安全转换、无效密文处理、失败行为和共享秘密导出；不直接把 toy 公钥加密当成 KEM。

04 / SIDE CHANNELS

时序、缓存与故障

检查与 secret 相关的分支、访存、拒绝采样行为，以及故障注入和密钥泄漏路径。

05 / BYTE LEVEL

编码与互操作

压缩、序列化、参数标识、边界长度和解析失败需要与规范一致；字节级偏差会影响兼容与安全。

06 / SYSTEM INTEGRATION

认证与密钥管理

协议须明确身份绑定、证书与签名、混合策略、回滚、密钥轮换和审计。只替换数学原语不会自动完成迁移。

教学仓库的边界

lattice-based-cryptography-samples ↗ 的 LLL、Toy LWE 和 Tiny Attack 用于学习，不具备标准参数、生产级随机数、常数时间防护或完整 KEM 安全转换。部署请使用经过审查、适配协议的成熟实现。
